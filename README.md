# Лабораторна робота №11: Робота з БД через Hibernate ORM (Jakarta Persistence)

## 1. Предметна область та опис сутностей

У межах предметної області **«Інтернет-магазин»** реалізовано об'єктно-реляційне відображення (ORM) за допомогою специфікації **Jakarta Persistence (JPA 3.2)** та її реалізації **Hibernate ORM 7.0.0.Final** поверх існуючої схеми бази даних **PostgreSQL (`shopdb`)** з `init.sql`.

### Ієрархія та класи сутностей:
1. **[`BaseEntity`](src/main/java/entity/BaseEntity.java) (`@MappedSuperclass`)**:
   - Містить спільні поля `id` (`Long`) та `name` (`String`), які успадковуються таблицями дочірніх сутностей без створення окремої таблиці в БД.
   - Первинний ключ позначено `@Id` та `@GeneratedValue(strategy = GenerationType.IDENTITY)`, що відповідає конструкції `BIGINT GENERATED BY DEFAULT AS IDENTITY` у `init.sql`.
   - Поле `name` має обмеження `@Column(name = "name", nullable = false, length = 100)`.
   - Містить `protected BaseEntity()` конструктор без параметрів (вимога специфікації JPA для інстанціювання через рефлексію та створення проксі).
   - Реалізує контракт `equals()` та `hashCode()` з урахуванням життєвого циклу JPA-сутностей та проксі-класів (`Hibernate.getClass(this)`): дві сутності рівні лише тоді, коли їхні ідентифікатори не є `null` і збігаються, а `hashCode()` повертає стабільне значення для класу сутності, щоб об'єкт не губився у `HashSet`/`HashMap` після виконання `em.persist()`.

2. **[`Category`](src/main/java/entity/Category.java) (`@Entity`, таблиця `categories`)**:
   - Успадковує `id` та `name` від `BaseEntity`.
   - Поле `description` відображено з `@Column(name = "description", length = 255)`.
   - Містить колекцію товарів `List<Product> products` зі зв'язком `@OneToMany(mappedBy = "categoryEntity", fetch = FetchType.LAZY, cascade = {CascadeType.PERSIST, CascadeType.MERGE}, orphanRemoval = false)`.
   - Має допоміжні методи синхронізації двоспрямованого зв'язку `addProduct(Product)` та `removeProduct(Product)`.

3. **[`Product`](src/main/java/product/Product.java) (`@Entity`, таблиця `products`)**:
   - Успадковує `id` та `name` від `BaseEntity`.
   - Поле `price` (`BigDecimal`) відображено з `@Column(name = "price", nullable = false, precision = 10, scale = 2)`, що точно відповідає `DECIMAL(10, 2) NOT NULL` у `init.sql`.
   - Поле `quantity` (`int`) відображено з `@Column(name = "quantity", nullable = false)`.
   - Містить посилання на категорію `Category categoryEntity` з анотаціями `@ManyToOne(fetch = FetchType.LAZY, optional = false)` та `@JoinColumn(name = "category_id", nullable = false)`.
   - Допоміжне поле `categoryId` позначено анотацією `@Transient` (не зберігається в БД напряму через Hibernate, але забезпечує зворотну сумісність зі старим JDBC- та InMemory-кодом).
   - Підкласи `Clothing`, `Electronics` та `Smartphone` залишені звичайними доменними класами (не `@Entity`), оскільки реляційна схема `init.sql` містить єдину таблицю `products` без дискримінатора.

## 2. Архітектура та конфігурація Hibernate (`persistence.xml` і `JpaUtil`)

- Конфігурація persistence-unit `internet-shop` розміщена у стандартному файлі [`src/main/resources/META-INF/persistence.xml`](src/main/resources/META-INF/persistence.xml).
- Клас [`JpaUtil`](src/main/java/jpa/JpaUtil.java) реалізовано за патерном **Singleton**:
  - Створює один екземпляр `EntityManagerFactory` на весь час роботи застосунку, динамічно підтягуючи параметри підключення (`db.url`, `db.user`, `db.password`) із локального файлу `application.properties`.
  - На кожну логічну операцію в методах `executeInTransaction(...)`, `executeInTransactionWithResult(...)` та `executeReadOnly(...)` створює окремий `EntityManager` у блоці `try-with-resources` (JPA 3.2 `AutoCloseable`) та гарантовано закриває його після завершення операції.
- Сервіси [`HibernateCategoryService`](src/main/java/service/HibernateCategoryService.java) та [`HibernateProductService`](src/main/java/service/HibernateProductService.java) реалізують ті самі інтерфейси `CRUDService<Category>` та `ProductService`, що й попередні реалізації (`InMemoryProductService`, `JdbcProductService`). Клієнтський код працює з ними поліморфно через інтерфейс `ProductService`.

### Демонстрація перевірки схеми (`hibernate.hbm2ddl.auto = validate`)
У `persistence.xml` встановлено режим `validate`. При старті застосунку Hibernate звіряє метадані анотацій `@Entity` із фактичною структурою таблиць у PostgreSQL, створеною скриптом `init.sql`.

Якщо змінити в класі `Category` анотацію колонки на невідповідну таблиці в БД, наприклад:
```java
@Column(name = "description_wrong", length = 255)
private String description;
```
то під час ініціалізації `EntityManagerFactory` Hibernate зупиняє запуск із помилкою `SchemaManagementException`:
```text
jakarta.persistence.PersistenceException: Unable to build Hibernate SessionFactory [persistence unit: internet-shop]
Caused by: org.hibernate.tool.schema.spi.SchemaManagementException:
    Schema-validation: missing column [description_wrong] in table [categories]
```

## 3. Двоспрямований зв'язок «Один до багатьох» (Рівень 2)

Між сутностями `Category` (один) та `Product` (багато) налаштовано двоспрямований зв'язок `@OneToMany` / `@ManyToOne`.

### Чому власником зв'язку (Owning Side) є `Product` (`@ManyToOne`)?
У реляційній моделі даних зв'язок «один до багатьох» реалізується через зовнішній ключ (`FOREIGN KEY (category_id) REFERENCES categories(id)`), який фізично міститься у таблиці дочірньої сутності **`products`**.
- **Власник зв'язку (Owning Side)** — це та сторона об'єктної моделі, яка відповідає за колонку зовнішнього ключа в таблиці БД. Тому власником зв'язку обов'язково є `Product` (сторона `@ManyToOne` з анотацією `@JoinColumn(name = "category_id", nullable = false)`).
- **Зворотна сторона (Inverse Side)** — клас `Category` (сторона `@OneToMany(mappedBy = "categoryEntity")`). Атрибут `mappedBy` вказує Hibernate, що конфігурацію зовнішнього ключа слід брати з поля `categoryEntity` класу `Product`, і що зміни лише у списку `category.getProducts()` без встановлення `product.setCategoryEntity(category)` не оновлюватимуть колонку `category_id` у БД.
- Саме тому в класі `Category` реалізовані допоміжні методи **`addProduct(Product)`** та **`removeProduct(Product)`**, які одночасно оновлюють і колекцію `products`, і посилання `product.setCategoryEntity(this)`.

### Обґрунтування вибору `FetchType.LAZY`, `cascade` та `orphanRemoval`
1. **Стратегія завантаження `FetchType.LAZY` на обох сторонах (`@OneToMany` та `@ManyToOne`)**:
   - За замовчуванням у специфікації JPA `@OneToMany` має `LAZY`, але `@ManyToOne` має `EAGER`. Ми явно встановили `fetch = FetchType.LAZY` для обох сторін, щоб уникати автоматичного завантаження пов'язаних об'єктів тоді, коли вони не потрібні, і контролювати вибірку явно через `JOIN FETCH` у JPQL.
2. **Вибір `cascade = {CascadeType.PERSIST, CascadeType.MERGE}` та `orphanRemoval = false`**:
   - У нашій схемі БД (`init.sql`) для зовнішнього ключа встановлено суворе обмеження **`ON DELETE RESTRICT`**:
     ```sql
     FOREIGN KEY (category_id) REFERENCES categories (id) ON DELETE RESTRICT
     ```
   - Це бізнес-правило захищає каталог товарів від випадкового видалення категорії разом з усіма її товарами.
   - Якби ми вказали `CascadeType.REMOVE` (або `CascadeType.ALL`) чи `orphanRemoval = true`, Hibernate автоматично генерував би `DELETE FROM products` при видаленні категорії або вилученні товару з колекції, що суперечить правилу безпеки `ON DELETE RESTRICT`.
   - Натомість `CascadeType.PERSIST` та `CascadeType.MERGE` дозволяють зручно зберігати та оновлювати нову категорію разом із доданими до неї товарами (`category.addProduct(p); em.persist(category);`), не створюючи ризику каскадного знищення даних.

## 4. Типові проблеми ORM: відтворення та виправлення (Рівень 3)

### 4.1. Проблема №1: `LazyInitializationException`

**Причина виникнення:**
Колекція `Category.products` налаштована зі стратегією `FetchType.LAZY`. Коли ми завантажуємо категорію методом `categoryService.findById(id)`, Hibernate повертає об'єкт `Category`, у якому замість реального списку товарів міститься проксі-колекція (`PersistentBag`). Як тільки метод `findById` завершується, `EntityManager` закривається, і сутність переходить у стан **detached**. Спроба звернутися до `detachedCategory.getProducts().size()` поза відкритим `EntityManager` призводить до винятку:

```text
org.hibernate.LazyInitializationException: failed to lazily initialize a collection of role: entity.Category.products: could not initialize proxy - no Session
```

**Чому не слід «лікувати» це переведенням на `FetchType.EAGER`?**
Глобальне увімкнення `EAGER` призводить до того, що при кожному зверненні до `Category` (навіть коли товари взагалі не потрібні) Hibernate завжди тягнутиме всі товари з БД, перевантажуючи пам'ять і породжуючи проблему `N+1`.

**Правильне виправлення (`LEFT JOIN FETCH`):**
У методі `HibernateCategoryService.findByIdWithProducts(long id)` використано JPQL-запит із `LEFT JOIN FETCH`, який ініціалізує категорію та її колекцію товарів одним SQL-запитом ще під час відкритого `EntityManager`:

```java
SELECT DISTINCT c FROM Category c LEFT JOIN FETCH c.products WHERE c.id = :id
```

Згенерований Hibernate SQL:
```sql
select
    distinct c1_0.id,
    c1_0.description,
    c1_0.name,
    p1_0.category_id,
    p1_0.id,
    p1_0.name,
    p1_0.price,
    p1_0.quantity 
from
    categories c1_0 
left join
    products p1_0 
        on c1_0.id=p1_0.category_id 
where
    c1_0.id=?
```

### 4.2. Проблема №2: Проблема `N+1` запитів

**Причина виникнення:**
У методі `countProductsPerCategoryWithNPlusOne()` ми спочатку завантажуємо список усіх категорій (`SELECT c FROM Category c`), що виконує **1 SQL-запит** (повертає $N = 3$ категорії). Потім у циклі `for (Category c : categories)` звертаємося до `c.getProducts().size()`. Оскільки колекція `products` є лінивою, для кожної з $N$ категорій Hibernate виконує окремий додатковий SQL-запит `SELECT ... FROM products WHERE category_id = ?`. Разом отримуємо **$1 + N = 4$ SQL-запити** (підраховано програмно через `Hibernate Statistics`: `stats.getPrepareStatementCount()`).

**Виведення SQL-запитів ДО виправлення (`4 запити` для 3 категорій):**
```sql
-- Запит 1: отримання списку всіх категорій (1)
select c1_0.id, c1_0.description, c1_0.name from categories c1_0 order by c1_0.id

-- Запити 2..4: підвантаження товарів для кожної з N=3 категорій у циклі (+3)
select p1_0.category_id, p1_0.id, p1_0.name, p1_0.price, p1_0.quantity from products p1_0 where p1_0.category_id=?
select p1_0.category_id, p1_0.id, p1_0.name, p1_0.price, p1_0.quantity from products p1_0 where p1_0.category_id=?
select p1_0.category_id, p1_0.id, p1_0.name, p1_0.price, p1_0.quantity from products p1_0 where p1_0.category_id=?
```

**Виправлення через `LEFT JOIN FETCH` (`1 запит` замість `4`):**
У методі `countProductsPerCategoryWithJoinFetch()` використано запит:
```java
SELECT DISTINCT c FROM Category c LEFT JOIN FETCH c.products ORDER BY c.id ASC
```
Завдяки цьому Hibernate виконує **рівно 1 SQL-запит із `LEFT JOIN`** і одразу заповнює колекції `products` для всіх категорій:
```sql
select
    distinct c1_0.id,
    c1_0.description,
    c1_0.name,
    p1_0.category_id,
    p1_0.id,
    p1_0.name,
    p1_0.price,
    p1_0.quantity 
from
    categories c1_0 
left join
    products p1_0 
        on c1_0.id=p1_0.category_id 
order by
    c1_0.id
```

| Варіант виконання | JPQL-запит | Кількість SQL-запитів (`Statistics`) |
|---|---|---|
| **До виправлення (`N+1`)** | `SELECT c FROM Category c` + обхід у циклі | **4** (`1 + 3`) |
| **Після виправлення (`JOIN FETCH`)** | `SELECT DISTINCT c FROM Category c LEFT JOIN FETCH c.products` | **1** |

> **Застереження щодо поєднання `JOIN FETCH` колекцій (`@OneToMany`) із пагінацією (`setFirstResult` / `setMaxResults`):**
> Якщо застосувати `JOIN FETCH` для колекції `@OneToMany` (наприклад, `Category` -> `products`) разом із пагінацією, реляційний `JOIN` розмножує рядки батьківської сутності пропорційно кількості дочірніх елементів. Через це Hibernate не може використати SQL `LIMIT / OFFSET` (інакше обрізалися б елементи колекції) і видає попередження `HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory`, завантажуючи **всю таблицю в оперативну пам'ять**. Натомість для зв'язку `@ManyToOne` (`Product` -> `categoryEntity` у `HibernateProductService.findPage()`) `JOIN FETCH` є абсолютно безпечним із пагінацією, бо кожному товару відповідає лише один рядок категорії, і Hibernate генерує штатний SQL `OFFSET ? ROWS FETCH FIRST ? ROWS ONLY`.

## 5. Інструкція із запуску проєкту

### Передумови:
- Java JDK 25;
- Apache Maven 3.9+;
- Запущений сервер **PostgreSQL** із базою даних `shopdb`.

### Кроки запуску:
1. Створіть тестову базу даних у PostgreSQL (якщо ще не створена):
   ```sql
   CREATE DATABASE shopdb;
   ```
2. Налаштуйте файл `src/main/resources/application.properties` за зразком `application.properties.example`:
   ```properties
   db.url=jdbc:postgresql://localhost:5432/shopdb
   db.user=postgres
   db.password=YOUR_PASSWORD
   db.pool.max-size=5
   ```
3. Скомпілюйте та запустіть демонстрацію:
   ```bash
   mvn clean compile exec:java
   ```
   Під час запуску `CrudDemo`:
   - виконується `DatabaseInitializer.init()` (перевіряє наявність таблиць за `init.sql`);
   - ініціалізується `JpaUtil` з перевіркою схеми `hibernate.hbm2ddl.auto = validate`;
   - виконується повний цикл CRUD з порожньої БД, перевірка кешу першого рівня (`a == b`), каскадне збереження двоспрямованого зв'язку `@OneToMany`/`@ManyToOne`, JPQL-запити з іменованими параметрами та пагінацією, відтворення і виправлення `LazyInitializationException` та проблеми `N+1` (із точним підрахунком запитів через Hibernate Statistics), а також демонстрація поліморфізму всіх трьох реалізацій `ProductService` (`InMemory`, `JDBC`, `Hibernate`).
