# Лабораторна робота №5: Рефакторинг програмного коду із застосуванням паттернів проєктування

## Предметна область: Інтернет-магазин

Робота є логічним продовженням та рефакторингом ЛР №1–4. Її мета — застосувати патерни проєктування GoF для покращення архітектури та усунення структурних проблем коду (жорстка прив'язка до конкретних класів, порушення принципу відкритості/закритості OCP, розгалужені умовні конструкції створення об'єктів).

---

## Рівень 1. Базовий (Factory Method)

### 1. Знайдена проблема в коді (До рефакторингу):
- У клієнтському коді (`Main.java`) у методі `checkout` вибір конкретного класу доставки (`StandardDelivery`, `ExpressDelivery`, `PickupDelivery`) залежав від розгалуженої умовної конструкції `if / else if`.
- У кількох місцях програми об'єкти стратегій знижок (`ThresholdDiscount`, `PromoCodeDiscount`, `NoDiscount`) створювалися напряму через оператор `new`.
- **Наслідок порушення OCP:** якщо в магазині з'являється новий спосіб доставки, розробник був змушений змінювати клієнтський код `Main.java`, додаючи новий `else if` та новий `new`.

### 2. Реалізоване рішення:
- Створено клас-фабрику **`DeliveryFactory`** (пакет `delivery`) зі статичним фабричним методом `createDelivery(int choice)`, який приймає числовий код вибору та через `switch` повертає потрібну реалізацію інтерфейсу `Delivery`. Всі власні класи доставок (`StandardDelivery`, `ExpressDelivery`, `PickupDelivery`) наслідують `AbstractDelivery`, де розрахунок побудовано за патерном **Template Method** (`getBaseCost(orderSum) + getAdditionalCost(orderSum)`).
- Створено клас-фабрику **`DiscountFactory`** (пакет `discount`) з фабричним методом `createDiscount(String promoCode)`. У `ThresholdDiscount` усунено дублювання порогів через окремий enum **`DiscountTier`** із конструкцією `switch (tier)`.
- У клієнтському коді (`Main.java`) повністю прибрано розгалуження `if-else` та прямі виклики `new` для доставок і знижок — створення об'єктів повністю делеговано фабрикам.

### 3. Яку проблему вирішив цей рефакторинг:
- **Дотримання принципу OCP (Open/Closed Principle):** клієнтський код `Main.java` закритий для модифікацій при додаванні нових способів доставки чи знижок.
- **Зниження зв'язності (Loose Coupling):** клас `Main` тепер взаємодіє лише з абстрактними інтерфейсами (`Delivery`, `DiscountStrategy`) та фабриками, не знаючи про конкретні класи реалізацій.
- **Єдина ієрархія та Template Method:** усунуто неоднорідність наслідування — усі власні способи доставки тепер наслідують базовий `AbstractDelivery`, реалізуючи єдиний алгоритм розрахунку (базова ставка + націнка). Єдиний клас, що реалізує `Delivery` напряму — це `NovaPoshtaAdapter` (зовнішня інтеграція через Adapter).
- Додавання будь-якого нового способу доставки тепер вимагає створення лише нового класу та одного рядка `case` у `DeliveryFactory`, залишаючи `Main.java` недоторканим.

## Рівень 2. Середній (Observer)

### 1. Знайдена ситуація в предметній області:
- При оформленні покупки в інтернет-магазині успішна зміна стану замовлення повинна сповіщати незалежні модулі системи:
  1. Систему звітності та обліку (бухгалтерію) для логування кожної транзакції.
  2. Систему клієнтського сервісу для відправки SMS-повідомлення покупцю на його валідований номер телефону.

### 2. Реалізоване рішення:
- Створено інтерфейс спостерігача **`OrderObserver`** (пакет `observer`) з методом оновлення `onOrderPlaced(...)`.
- Реалізовано два конкретні спостерігачі:
  - **`OrderLogger`** — фіксує інформацію про продаж товару для бухгалтерії.
  - **`CustomerNotifier`** — надсилає імітоване SMS-сповіщення клієнту на номер його телефону.
- Клас **`Order`** виступає у ролі **Subject (Суб'єкта)**: зберігає список підписників `List<OrderObserver>`, надає метод підписки `addObserver(...)` та автоматично сповіщає всіх підписників через `notifyObservers()` після завершення покупки.

### 3. Яку проблему вирішив рефакторинг:
- **Принцип єдиної відповідальності (SRP):** логіка замовлення відокремлена від побічних задач (логування та відправка повідомлень).
- **Слабка зв'язаність (Loose Coupling):** клас `Order` взаємодіє з підписниками виключно через інтерфейс `OrderObserver`. Додавання нових підписників (наприклад, Telegram-бота або email-розсилки) не вимагає внесення жодних змін у клас `Order`.

## Рівень 3. Високий (Adapter)

### 1. Змодельована ситуація несумісності інтерфейсів:
- До системи інтернет-магазину інтегровано зовнішній сервіс доставки **`NovaPoshtaService`** (імітація сторонньої бібліотеки / зовнішнього API).
- Код сторонньої бібліотеки не можна змінювати, але її інтерфейс повністю несумісний з очікуваним у нашій системі інтерфейсом `Delivery`:
  - У системі метод називається `calculateCost(double orderSum)`, а в сторонньому сервісі — `computeTariff(int valueInKopiyky)`.
  - У системі розрахунки ведуться у гривнях (`double`), а в сторонньому API — у копійках (`int`).
  - Метод отримання назви служби називається `getServiceTitle()` замість `getName()`.

### 2. Реалізоване рішення:
- Створено клас-адаптер **`NovaPoshtaAdapter`** (пакет `delivery`), який реалізує цільовий інтерфейс `Delivery`.
- Адаптер містить посилання на сторонній об'єкт `NovaPoshtaService` (патерн реалізовано через **композицію**, а не наслідування).
- Метод `calculateCost(double orderSum)` адаптера перекладає виклики:
  1. Конвертує гривні (`double`) у копійки (`int`).
  2. Викликає несумісний метод стороннього сервісу `novaPoshta.computeTariff(...)`.
  3. Конвертує отриманий результат з копійок назад у гривні (`double`).

### 3. Обґрунтування застосування патерна на захисті:
- Ми застосували саме патерн **Adapter**, оскільки не маємо права та можливості модифікувати код сторонньої бібліотеки `NovaPoshtaService`.
- Адаптер дозволяє підключити зовнішній сервіс до нашої `DeliveryFactory` без зміни існуючої архітектури системи.

```cmd
run.bat
```

```powershell
javac -encoding UTF-8 -sourcepath src -d out src\Main.java
java -cp out -Dfile.encoding=UTF-8 Main
```
